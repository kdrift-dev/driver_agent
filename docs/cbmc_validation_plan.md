# CBMC Validation Plan (Feasibility Notes)

## 1) Why runtime Bug Validator is hard for hardware-dependent drivers
- Many driver modules require specific physical devices, firmware states, or bus topology (PCI/USB/I2C/SPI) that are not present in generic CI/QEMU runs.
- System-level suites generated by LLM may compile and boot but still cannot trigger meaningful probe/IRQ/PM paths without hardware.
- A "passed" generic KUnit/QEMU run can therefore be non-informative for module migration correctness.

## 2) Obligations suitable for early CBMC integration
- Return-value convention updates:
  - verify updated API return handling (`0`/`ERR_PTR`/negative errno branches).
- Error-path cleanup:
  - ensure cleanup paths still release all resources after API migration.
- Null checks:
  - verify dereference preconditions for migrated helper/API outputs.
- Resource pairing in sliced code:
  - `alloc/free`, `get/put`, `register/unregister`, `enable/disable`.
- Simple locking preconditions:
  - assert lock must be held before critical call; unlock on all exits.

## 3) What is not suitable initially
- Full hardware behavior modeling.
- Interrupt timing / scheduling realism.
- Real MMIO side effects and device state machines.
- Complex kernel-wide concurrency and cross-subsystem interactions.

## 4) How CBMC could be integrated later
- Input:
  - start from `affected_function_slices/<function>.c`.
- Environment modeling:
  - generate/stitch stubs for referenced kernel APIs and structs.
- Obligation encoding:
  - transform compatibility obligations into assertions/assumptions.
- Verification:
  - run bounded model checking on target function slices.
- Reporting:
  - emit pass/fail/unknown with violated obligation IDs and trace snippets.

## 5) Additional Driver-Agent metadata to output for CBMC readiness
- Per obligation:
  - machine-readable preconditions, postconditions, and confidence.
- Per affected function:
  - explicit resource/lock pairs and required context (caller/callback root).
- Symbol contract bundle:
  - normalized old/new API contract summary (arguments, return conventions, ownership hints).
- Slice dependency map:
  - direct callees, required macros/types/fields, and stub priority list.
- Assertion candidates:
  - draft assertions derived from `hard_checks`/`semantic_checks` for automatic harness generation.
