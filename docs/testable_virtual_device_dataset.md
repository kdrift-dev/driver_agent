## Issues Found and Fixed

1. Definition location was too slow on larger modules because it processed many symbols serially and searched unconstrained struct fields. Fixed by parallelizing per-symbol definition lookup with `--jobs` and skipping field lookup when the owner struct is unknown.

2. Kernel-side helper discovery was too permissive. It inferred false semantic migration signals such as `mutex_lock -> refcount_dec_and_mutex_lock`, `psp_dev_create -> may_create_dentry`, and `ns_capable -> bpf_net_capable`. Fixed by requiring non-generic token relation plus old-driver contextual support, and by excluding generic lock/list/BPF/capability tokens.

3. Helper evidence was bloated because every helper signal repeated the entire kernel-side helper diff path list. Fixed by storing only paths for the actual replacement candidates on each symbol item.

## Recommended Use

Use these as a staged dataset:

1. `drivers/gpu/drm/vkms`: first full-flow in-tree case because KUnit is already supported and the prompt size is controlled.
2. `drivers/dma-buf/heaps`: runnable kselftest case; smaller, but useful for QEMU/kselftest demonstration.
3. `drivers/net/netdevsim`: large virtual-device case for analysis scalability and future isolated kselftest runner work.
4. `drivers/net/wireguard`: large software-device case with upstream QEMU harness; useful but likely requires dedicated userspace dependency handling.
5. `drivers/block/null_blk`: useful virtual-device smoke case if we add a custom QEMU configfs/block IO check.

Current boundary: the analysis pipeline can handle ~6-7K LOC modules after the helper-discovery fix, but runtime validation is only strong for modules with currently supported deterministic KUnit/kselftest runners.
